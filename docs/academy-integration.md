# Academy applications: database and notification email

The Academy form submits JSON to the same-origin `POST /api/academyLeads` endpoint. Production nginx must continue forwarding `/api` to monsoonback, as it does for existing forms. Deploy both repositories, with the backend first.

## Request

```json
{
  "fullName": "Test Applicant",
  "phoneNumber": "+91 9999900000",
  "email": "applicant@example.com",
  "contactConsent": true,
  "submissionId": "ef6341bf-30dc-4bc6-8b5c-e185fe48c731"
}
```

`submissionId` is a UUID v4 generated by the form and retained for retries of an unchanged submission. Phone numbers are strings. Only validated fields are stored. Consent is required and timestamped server-side.

## Backend

Reviewed backend files are in `docs/academy-backend`, with a bounded installer at `scripts/install-academy-backend.cjs`. It adds four files to `D:/Work/monsoonback` and registers `POST /academyLeads` on its existing `/api` router. Run `node scripts/install-academy-backend.cjs --check` to preview, then run without `--check` to install when filesystem permissions allow it. It refuses to overwrite different existing Academy files.

The model uses monsoonback's existing Mongoose connection and explicitly selects collection `academy_leads`; no separate database or database credentials are needed. MongoDB creates the collection on use. Before accepting live submissions, verify the unique `submissionId` index exists (normal Mongoose automatic indexing creates it unless disabled by deployment configuration).

The handler saves first, then uses the existing Nodemailer service. The defaults match the current franchise form:

- From: `enquiry@theprofessionalworld.com`
- To: `shubhi@theprofessionalworld.com`
- Subject: `New ARYA Fellowship Academy Lead`

Optional server environment variables `ACADEMY_MAIL_FROM` and `ACADEMY_MAIL_TO` override those addresses. Existing mail authentication remains in the backend's current `emailService`; no credentials are copied into the frontend or this bundle.

Successful save returns HTTP 201 with `{"message":"Application received.","data":{"saved":true}}`. An identical submission ID returns HTTP 200 without another insert or email. Invalid input returns 400; database failure returns 503 and sends no email. The frontend only confirms success when the response explicitly contains `data.saved: true`.

Email failure does not reject a saved lead. `emailStatus` records `pending`, `sent` (accepted by the mail transport, not confirmed inbox delivery), or `failed`, with attempt/sent timestamps. Automatic notification retry is not included; failed or stale pending notifications require follow-up. If notification-status recording fails, the saved application is still accepted and the server logs the failure.
